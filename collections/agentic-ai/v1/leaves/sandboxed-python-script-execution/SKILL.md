# sandboxed-python-script-execution

## Summary

Execute LLM-generated Python file-generation scripts inside a Docker-based Python sandbox (virtualenv with pre-installed third-party libraries and command-line tools) so that required input files for assembled fuzzing commands can be produced safely and reproducibly.

## When to use

Use when LLM-proposed commands reference file placeholders whose actual input files must be generated by untrusted, model-written Python scripts before fuzzing or command execution.

## When NOT to use

- When the required input files already exist (e.g., seeds are provided directly) — no script execution is needed
- When the generated scripts are written by a trusted human rather than an LLM and the host environment is already isolated

## Inputs

- LLM-generated Python file-generation scripts (one per assembled command's file needs)
- Assembled commands containing file placeholders (from Command Assembly, generateCommands)
- Docker base image with virtualenv and pre-installed third-party libraries and CLI tools

## Outputs

- Files produced by the sandboxed scripts (test inputs for the commands)
- Resolved command-to-file mappings saved to resolved_commands, where every file placeholder is bound to an existing generated file

## How to apply

Build a Docker-based Python sandbox from a virtualenv that pre-installs the libraries and command-line tools the generated scripts may need (ProphetFuzz pre-installs 33 commonly used third-party libraries and 36 CLI tools for subprocess calls). Run each LLM-generated Python file-generation script inside this isolated environment so script side effects are contained. Collect the files produced by the sandboxed scripts and compare them against the file placeholders referenced in the assembled commands: exclude any command whose crucial input files were not successfully generated, and apply a prefix-matching heuristic to remap unexpectedly named produced files to the placeholders that expect them. The rationale is to satisfy ProphetFuzz challenge C3 (obtaining the files commands require) without executing arbitrary model-generated code on the host, while retaining commands whose files can be resolved under a slightly different name.

## Examples

```
docker run -it --privileged=true prophetfuzz bash  # full ProphetFuzz image; then: bash run_all_in_one.sh bison
```

## Evaluation signals

- Every command retained in resolved_commands has all of its file placeholders bound to an existing generated file (verified with a file_exists check per mapping)
- No command referencing a missing crucial file appears in the output — commands with fewer generated files than placeholders are excluded
- Prefix-matching remaps only unexpectedly named files; commands whose files cannot be corrected are excluded, not silently kept
- Sandbox execution produces no side effects outside the Docker container (isolation invariant)
- Spot-check a resolved mapping by running the bound command and confirming the program accepts the generated input file

## Limitations

- Scripts whose generated files cannot be matched to placeholders (even by prefix correction) are discarded, so usable commands may be lost
- The sandbox only covers libraries and CLI tools it pre-installed (33 libraries, 36 tools in ProphetFuzz); scripts needing other dependencies will fail
- The prefix-matching heuristic is a name-correction heuristic and could in principle bind a produced file to the wrong placeholder
