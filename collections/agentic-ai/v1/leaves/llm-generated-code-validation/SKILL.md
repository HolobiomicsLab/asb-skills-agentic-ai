# llm-generated-code-validation

## Summary

Validate LLM-generated Python file-generation scripts by executing them in a Docker/virtualenv Python sandbox and checking that the produced files satisfy the file placeholders of assembled commands, applying a prefix-matching name-correction heuristic before fuzzing.

## When to use

Use when assembled LLM-proposed commands reference file placeholders that must be bound to real files generated by LLM-written Python scripts, and unexecutable commands must be filtered out before fuzzing.

## When NOT to use

- The goal is to validate constraints between command-line options (Section 3.2 Constraint Extraction), not to resolve generated input files
- The scripts being executed were not LLM-generated and their provenance/trustworthiness is already established by other means
- Only the LLM-interaction part of the pipeline is needed — the README notes the pre-installed base image suffices 'if you only want to complete the part that interacts with the LLM'

## Inputs

- LLM-generated Python file-generation scripts (from Command Assembly output, Section 3.4)
- Assembled commands containing file placeholders (e.g. '@@' input-file markers)
- Docker sandbox image pre-installed with virtualenv, 33 Python libraries, and 36 command-line tools

## Outputs

- resolved_commands: set of executable commands with every file placeholder bound to an existing generated file
- Set of excluded commands whose crucial input files were not generated or could not be name-corrected
- Remapped file-name corrections produced by the prefix-matching heuristic

## How to apply

Run each LLM-generated Python file-generation script (Section 3.5 'File Generation') inside a Docker-based Python sandbox built with virtualenv that pre-installs 33 commonly used third-party libraries and 36 command-line tools for subprocess calls. Collect the files produced by the sandboxed scripts and compare them against the file placeholders referenced in the assembled commands. Exclude any command whose crucial input files were not successfully generated, since a command with fewer produced files than placeholders cannot run. Apply a prefix-matching heuristic (code fixer step) to remap unexpectedly named produced files to the placeholders that expect them rather than discarding the associated commands, excluding commands that cannot be corrected. Save the surviving commands together with their resolved file mappings for downstream corpus minimization and fuzzing.

## Related tools

- **ProphetFuzz** (Tool whose Section 3.5 File Generation stage executes LLM-generated scripts in a sandbox and resolves command file placeholders; implemented in fuzzing_handler (code_checker.py, cmd_fixer.py, generate_combination.py)) — https://github.com/NASP-THU/ProphetFuzz
- **Docker** (Provides the sandboxed Python execution environment for running LLM-generated file-generation scripts (Dockerfile builds the experiment environment, tested on Ubuntu 20.04))
- **Python** (Language of the LLM-generated file-generation scripts (~3k lines of Python) and of the validation/fixer logic)

## Examples

```
docker build -t prophetfuzz:latest . && docker run -it --privileged=true prophetfuzz bash run_all_in_one.sh bison
```

## Evaluation signals

- Every command retained in resolved_commands has all of its file placeholders bound to an existing generated file (verified with a file_exists check per mapping)
- No command referencing a missing crucial file appears in the output — the count of produced files must be at least the count of placeholders per command
- Remapped file names from the prefix-matching heuristic correspond to actually existing sandbox-produced files
- Commands excluded at this stage are exactly those whose file-generation scripts failed or produced fewer files than placeholders
- Downstream fuzzing (afl-fuzz with '@@' input-file marker) can launch each retained command without file-not-found errors

## Limitations

- Commands are excluded when fewer files than placeholders are produced, so hallucinated or failing LLM scripts silently drop option combinations from testing
- The prefix-matching heuristic can only correct unexpectedly named files that share a prefix with the expected placeholder name; commands that cannot be corrected are discarded
- If run outside the Docker environment, dependencies must be manually installed and fuzzing_handler/config. must be adjusted to point to the program under test
