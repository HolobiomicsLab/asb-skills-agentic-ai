# KB fact validity verification via constrained decoding

## Summary

Verifies that every token emitted by an LLM during fact generation lies on a valid path of a prefix tree built from verbalized knowledge-base facts, guaranteeing 100% of generated sequences correspond to existing KB facts rather than hallucinations.

## When to use

Use when an LLM decodes facts against a tokenized prefix-tree index of verbalized KB triples and you must prove each generated sequence forms an existing fact, checking token-by-token membership against allowed continuation sets.

## When NOT to use

- The facts are already retrieved explicitly by an external retriever pipeline rather than generated by the LLM — constrained generation is positioned as an alternative to retriever-based solutions
- You need free-form LLM generation over parametric knowledge (e.g. on Mintaka/WebQSP where LLM-only reached 82.0% and 80.5% accuracy and outperformed ReFactX)
- Your knowledge base cannot be tokenized/indexed in a prefix tree or the target fact strings are not expressible as discrete token paths

## Inputs

- Tokenized verbalized KB facts indexed in a prefix tree (e.g. 31k-facts in-memory demo index; Wikidata-derived ~800M-facts disk-backed index)
- LLM logits/probability distribution at each autoregressive decoding step (e.g. from Qwen2.5-3B)
- Prompts triggering the Fact command (recognized via In-Context Learning instruction)

## Outputs

- Masked logit vector with -infinity on all tokens outside the prefix-tree-allowed next-token set
- Generated token sequences that are guaranteed to form existing KB facts
- Per-test verification results JSON (e.g. constrained_decoding_verification.json) with pass/fail per token-sequence validity check

## How to apply

Install the ReFactX package in a virtualenv or conda environment with `pip install refactx[torch]`, then load the in-memory prefix tree derived from the 31k-facts knowledge base shipped with the try_refactx notebook. Implement a Huggingface LogitsProcessor that, at each decoding step of autoregressive generation, looks up the set of next tokens that continue a valid fact path in the prefix tree and sets the log-probabilities of all other vocabulary tokens to -infinity, so the masked logit vector leaves finite probability only on tree-consistent tokens. Run constrained generation with a small model such as Qwen2.5-3B under greedy and beam-search decoding (3 beams) on prompts where the model invokes the Fact command. Verify the allowed-set semantics directly: after a prefix such as '<Danny Boyle> <' the admissible continuation set must include 'date' but exclude 'born'. The acceptance criterion is that 100% of tokens emitted after Fact-command activation lie on valid prefix-tree paths; note that constrained generation only narrows the vocabulary — the final token choice always remains with the LLM's probability estimates. Record per-test results in a JSON artifact (e.g. constrained_decoding_verification.json) and expect only ~1.3% wall-clock overhead (4000 tokens: 303.89s constrained vs 300.14s unconstrained).

## Evaluation signals

- 100% of tokens emitted after Fact-command activation lie on valid prefix-tree paths
- The masked logit vector leaves finite probability only on tree-consistent tokens (all others set to -infinity)
- Admissible-continuation sanity check: after prefix '<Danny Boyle> <', 'date' is allowed but 'born' is excluded
- Every completed generated sequence matches an existing fact in the KB (e.g. among the 31k demo facts)
- Overhead stays near the reported ~1.3% time increase over unconstrained generation (303.89s vs 300.14s for 4000 tokens)

## Limitations

- Constrained generation guarantees only KB-consistency, not correctness of the LLM's choice among valid facts — the final token selection remains the LLM's probability estimate
- On Mintaka and WebQSP, ReFactX performed worse than LLM-only (82.0% and 80.5% accuracy), so valid-fact generation does not imply better answers on data covered by parametric knowledge
- The Bank dataset proved especially challenging, with precision up to only 51.3% and accuracy up to 42.8% despite valid-fact decoding
- Large Wikidata-scale indexes require the disk-backed prefix tree plus a key-value cache store (e.g. PostgreSQL) on the same machine; the demo notebook uses only a 31k-facts in-memory tree
