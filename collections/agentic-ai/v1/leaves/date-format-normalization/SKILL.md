# date-format-normalization

> **License: noncommercial** — confirm your use is a permitted (noncommercial) purpose before applying; commercial use requires a separate license (see `metadata.tool_license`). <!-- asb-license-banner -->
## Summary

A post-processing step in the classification-guided LVLM pipeline that standardizes generated structured entity records: date fields are converted to 'year-month' format, punctuation and capitalization are unified, and degenerate repeated-token artifacts are removed from generated values before validation and scoring.

## When to use

Use when raw LVLM (e.g., Qwen2.5-VL-7B) JSON predictions for document VIE must be standardized into entity-level field name/value pairs whose date values conform to the 'year-month' convention prior to benchmark scoring or validation.

## When NOT to use

- The input is the upstream OCR text or document image, not already-parsed model JSON output — this skill operates after the LVLM inference and JSON parsing stage
- The task requires fine-tuning the LVLM rather than post-processing its generated text — use the LoRA SFT workflow instead
- Document-type classification or dynamic prompt assembly is the target step — this skill begins only from the generated structured prediction

## Inputs

- Raw structured prediction (pure JSON string) generated by the Qwen2.5-VL-7B LVLM from the classification-conditioned prompt plus document image
- Entity-level field name / value pairs parsed from the model output
- Prompt-specified landmark field list indicating which fields are date fields

## Outputs

- Normalized entity-level field name / value pairs with date fields in 'year-month' format
- Validated pure-JSON structured entity record with exactly the requested landmark fields and 'unidentified' for missing/unreadable values

## How to apply

After parsing the Qwen2.5-VL-7B raw output as JSON into entity-level field name/value pairs, iterate over the record and (1) convert any recognized date values to the 'year-month' format required by the prompt, (2) unify punctuation and capitalization across generated values, and (3) strip obvious repetition artifacts (degenerate repeated-token outputs) that the LVLM may emit. Then validate that the output is pure JSON containing exactly the requested landmark fields, that missing or unreadable entities are filled with 'unidentified', and that date fields conform to 'year-month'. These standardizations matter because pipeline-level acceptance is measured with entity-level F1 (86.43%) and normalized edit distance (0.9012), which are sensitive to formatting drift and degenerate repeats.

## Related tools

- **Qwen2.5-VL-7B** (Zero-shot LVLM whose raw generated JSON prediction is the object of normalization; its degenerate repeated-token outputs are the artifacts this step removes)

## Examples

```
python -c "import ; rec=.load(open('pred.')); rec['issue_date']=rec['issue_date'][:7].replace('/','-'); rec['valid_until']=rec['valid_until'][:7].replace('/','-'); .dump(rec, open('pred_norm.','w'), ensure_ascii=False)"
```

## Evaluation signals

- Output parses as valid pure JSON containing exactly the requested landmark fields
- All date fields conform to the 'year-month' convention
- Missing or unreadable entities are filled with 'unidentified' rather than left empty or hallucinated
- No degenerate repeated-token sequences remain in generated values
- Post-processed record scores at pipeline-level benchmarks: entity-level F1 of 86.43% and NED of 0.9012 for the zero-shot framework

## Limitations

- Normalization is rule-based on generated text; it cannot recover values the LVLM failed to read due to seals, watermarks, or low contrast in the document image
- Date normalization assumes the prompt instructed 'year-month' format; records from prompts with different landmark conventions will not align
- The LVLM inference and post-processing stage is described as an architectural component rather than an independently validated stage
