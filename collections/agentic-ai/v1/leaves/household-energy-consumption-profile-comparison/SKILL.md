# Household Energy Consumption Profile Comparison

## Summary

Compares hourly household energy consumption profiles generated by the WattCouncil pipeline under two alternative weather sources (TMY real-weather data vs. LLM-generated weather) to quantify whether the choice of weather source meaningfully shapes the generated consumption routines.

## When to use

Use when two WattCouncil run outputs exist (one with TMY weather, one with LLM-weather baseline) and the goal is to tabulate deltas in hourly consumption distributions to test weather-source sensitivity.

## When NOT to use

- Only one weather-source run exists — the deltas require matched records from both the TMY-weather run and the LLM-weather baseline run
- The goal is validating generated profiles against measured load data (e.g., the CER dataset) rather than comparing two synthetic weather-source conditions
- Stage 1 family or Stage 3 council settings were changed between the two runs, since matched family/variant records are required for a valid delta table

## Inputs

- stage3_consumption_*. JSON consumption outputs from a TMY-weather WattCouncil run
- stage3_consumption_*. JSON consumption outputs from an LLM-weather baseline WattCouncil run
- stage2_hourly_*. weather artifacts from both runs (for plausibility checks)
- family/variant identifiers from Stage 1 family generation for record matching

## Outputs

- CSV files of consumption outputs for both runs (via scripts/convert_outputs.py)
- Comparison table of hourly consumption deltas between the two weather sources with matched family/variant records

## How to apply

Run the WattCouncil pipeline twice, keeping Stage 1 family generation and Stage 3 consumption council settings unchanged, once with TMY weather enabled via `--weather-config config/weather.yaml` (routing Stage 2 through utils/tmy_weather.py) and once with the LLM-weather baseline. Convert the JSON consumption outputs of both runs to CSV using scripts/convert_outputs.py. Align records by family and variant so the comparison table contains matched pairs from both weather conditions, then compare the hourly consumption distributions and tabulate the deltas. Before trusting the deltas, validate that the TMY run's stage3_consumption_*. artifacts exist as valid JSON, that Stage 2 hourly weather values fall in physically plausible ranges (e.g., humidity below 100%), and that checkpoints were consumed from the raw/ directories.

## Examples

```
python main.py --config config/runtime.yaml --weather-config config/weather.yaml
```

## Evaluation signals

- The TMY run's stage3_consumption_*. files exist and are valid JSON
- Stage 2 hourly weather values in the TMY run fall in physically plausible ranges (e.g., humidity below 100%)
- The comparison table contains matched family/variant records for both weather conditions
- Checkpoints for both runs were consumed from the raw/ directories, confirming no generation steps were silently skipped
- Hourly consumption deltas are tabulated against aligned timestamps from the CSV conversions of both runs

## Limitations

- Comparability depends on holding Stage 1 family and Stage 3 consumption LLM council settings unchanged across runs; differing council settings confound the weather-source deltas
- The framework's checkpoint/corruption-detection system can skip invalid files, so a run with missing stage3_consumption_*. artifacts cannot be validly compared
- Physical plausibility of weather (e.g., humidity < 100%) is only checked via auditor/guidance rules, and failures feed a persistent knowledge_base.txt, so run-to-run behavior may differ across attempts
