# agent-response-generation

## Summary

The final stage of AudioFab's fixed tool learning control loop, in which the LLM Planner assembles a complete natural-language response only after every subtask in the planned toolchain has executed successfully, and the MCP Client delivers that response to the user.

## When to use

Use when implementing or auditing an LLM agent control loop where a final user-facing answer must be generated conditionally, i.e. gated on successful completion of all planned subtasks and tool execution results rather than emitted speculatively.

## When NOT to use

- When the agent framework is free-form/chat-style and must stream partial answers before tools finish — AudioFab's loop forbids emitting the final response before every subtask succeeds
- When tool execution results are unavailable or the MCP Server cannot return them; response generation in this design depends on planner-side evaluation of returned results
- When the task requires no toolchain — the planner's response stage here is defined relative to planned subtasks and tool invocations

## Inputs

- Natural-language user command received via the MCP Client
- Ordered subtask list produced by the LLM Planner
- Tool execution results returned from the MCP Server after each invocation
- Toolchain evaluations provided by the Tool Selection service

## Outputs

- A single complete natural-language response generated by the LLM Planner
- Final results (e.g. processed audio files, analysis text) delivered to the user by the MCP Client

## How to apply

Wire the Response Generation stage as the terminal step of the four-stage loop (task planning -> tool selection -> tool call/execution -> response generation). After the LLM Planner decomposes the user command into ordered subtasks and the MCP Client has executed each selected tool in its dedicated dependency environment, return execution results from the MCP Server to the planner so it can make subsequent decisions between subtasks. Only when all subtasks report success does the LLM Planner assemble the complete response, which the MCP Client then delivers to the user. The correctness criterion is that no response is emitted early: partial toolchains or failed subtasks must loop back through planning/invocation instead of triggering response assembly.

## Evaluation signals

- One natural-language command completes planning -> tool selection -> tool call/execution -> response generation end-to-end via python scripts/start_all.py
- The final response is emitted only after every subtask reports success — verify no response appears when a subtask fails or loops back
- The delivered response references the actual tool execution results returned by the MCP Server (e.g. separated accompaniment or emotion-analysis output), not hallucinated content
- For the demo use cases, the final response matches the expected artifacts: e.g. lip-synced digital-human video after speech emotion analysis, or music-style description of the separated instrumental track
- The MCP Client, not the LLM Planner directly, delivers the response to the user, consistent with the documented component responsibilities

## Limitations

- Response generation is gated on all subtasks succeeding, so a single failing tool (e.g. a locally undeployed FunTTS/Music/Audio Separator model whose registration was removed from servers_config.) prevents any final response
- The paper link is not yet available in the official revised version, so full-text verification of the response-generation stage relies on the README and source cards
- AudioFab is released under CC BY-NC 4.0 (non-commercial), restricting reuse of this loop design in commercial settings
